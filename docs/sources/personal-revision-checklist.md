# 学术论文修改要点（个人复用清单）

> 来源：《高阶数值格式忠实复现的编程智能体工作流》（投《航空学报》）修改过程中总结。
> 适用：中文学术期刊论文，同样适用于英文论文。写新论文、审查初稿、交给 AI 改稿时，可以直接附上本文件。

---

## 0. 总原则：论文写什么

一篇学术论文只回答五个问题：

1. **为什么做**：问题与动机，以及现有工作的不足。
2. **怎么做**：方法与设计。
3. **结果是什么**：实验与数据。
4. **发现了什么**：从结果中得到的规律与结论。
5. **有什么值得讨论**：适用范围、局限与后续方向。

任何不服务于这五个问题的句子，都应删除或改写。下面各条都是这一原则的具体化。

---

## 1. 强调创新点，次要内容一笔带过

- **问题**：用否定式自我降格，如"××是上述设计的实现形式，而非本文的主要创新"。
- **原因**：论文应正面陈述贡献。次要内容简要交代即可，不需要专门声明"这不是创新点"。
- **改法**：删掉否定式说明，把次要内容作为实现细节平铺叙述。

| 不推荐 | 推荐 |
|---|---|
| 技能包是上述设计的实现形式，而非本文的主要创新。 | 上述设计以技能包形式实现，便于统一调用。 |
| 本文并不声称已经实现了×× | 本文聚焦于××这一环节（范围界定写一次即可，放在引言或讨论中） |

## 2. 不写数据真实性或来源的"自证"句

- **问题**：如"以下实验均基于项目中已有的执行产物、Git 版本历史与逐次运行记录，本文对证据进行汇总与审计，未重新运行模型"。
- **原因**：写进论文的数据默认就是真实的、供同行学习和审查的。刻意强调"数据是真的、来源可查"，反而显得不自信，像内部审计备忘录。
- **改法**：直接写实验设置与结果。可复现性用"代码开源"一句话交代。

## 3. 术语使用领域内最普遍认可的形式

- **问题**：为了"规范"把通用术语强行译成冷僻中文，如 token→词元。
- **原因**：读者最熟悉哪种形式就用哪种。领域内通用的英文术语（token、agent、benchmark 等）可以直接使用，首次出现时用括号补一句解释。
- **改法**：首次出现写成"token（模型处理文本的基本单元）"，之后统一写 token。全文前后一致。

## 4. 不写工程笔记式的文件与存档信息

- **问题**：
  - "随稿保存逐次运行汇总、来源校验值、审计脚本"；
  - "随稿数据包包括 arm_data.csv（8 308 字节，SHA-256 前缀 efd4abaf）……"；
  - 正文里出现 commit hash、文件名、字节数、校验值、目录路径。
- **原因**：这些属于代码仓库 README 的内容，不属于论文。论文不说明"数据放在哪个文件里"。
- **改法**：
  - 正文或数据可用性声明只写一句："本文代码与数据已开源于 GitHub：<地址>。"
  - SHA-256、文件清单、提交号、复现步骤都写进仓库 README。

## 5. 不写写作过程与投稿流程的元信息

- **问题**：
  - "本文基于项目中已有的论文、技能包、代码与实验日志撰写"；
  - "未产生新的模型运行结果"；
  - "××信息将于正式投稿前补充"；
  - "作者信息投稿前补齐"。
- **原因**：读者不关心论文是怎么写出来的。待补信息是作者自己的待办事项，不应进入正文。
- **改法**：删除这类句子。真正缺的信息在源文件里留占位符（如 `<GitHub 地址>`），或用 LaTeX 注释 / Word 批注标记，正文不出现。

## 6. 附录只放确实需要放的内容

- **问题**：把核心数据表（如复现误差对比表、消融逐组汇总表）放进附录，正文只引用"见附录"。
- **原因**：支撑主要结论的数据应放在正文，读者无需跳转。附录只用于冗长推导、大量补充算例、对主线不必要的细节。
- **改法**：核心表格移回对应的正文小节。"可复查性"不需要单独成节，用一句开源声明代替。

## 7. 不口语化，不用借喻和行话

常见替换（"→"左侧为不推荐，右侧为推荐）：

- 承重结构 → 可靠性保障 / 关键结构要件（"承重"在力学期刊中会被按字面理解）
- 闸 → 检查关卡；地板 → 阈值 / 下限
- 兜底 → 补救；过测 → 通过测试
- 喂答案 → 提供答案；红线 → 基本约束
- 跑通 → 正常运行 / 完成；挑 → 选择；停在 → 中止于；补齐 → 补充完善
- 空壳 → 接口桩；探针 → 运行检测（CFD 中"探针"指流场测点，会撞词）；靶标 → 复现对象
- "下面不按时间罗列，只讲……" → "以下按问题类型归纳……"
- "这是提交数而非迭代轮数，……未被系统记录" → "需要指出，该统计量为版本提交数，并不等同于迭代轮数"
- "值得注意的是""一次也没有出现""无一例外" → 直接陈述事实
- "我们认为" → "本文认为"

**例外**：已经正式定义的分类名或术语（如"捷径""指纹""契约"），在首次出现时给出定义后可以保留，全文统一使用。

## 8. 局限与边界：写一次、写在讨论里、用学术方式写

- 局限要诚实，但应集中放在"讨论"部分，以"本文结论的适用范围存在以下边界"这类方式分点陈述。
- 不要在正文各处反复插入防御性说明，如"需要说明……并非……""不能据此宣称……"。保留必要的一两处统计口径说明即可。
- 局限是学术讨论，不是自我辩护，也不是备注。

## 9. 符合目标期刊的格式规定（以《航空学报》为例）

- **题目**：中文不超过 20 字，不用自定义缩略词。
- **摘要**：中文不少于 200 字，第三人称，不以"本文"作主语，不含公式和变量；英文摘要与中文对应。
- **引言**：不编节号，结尾只介绍要做的工作，不写结论。
- **结论**：分点写，只写结论，不重复背景与方法。
- **图表**：中英文双题，三线表，单栏图宽不超过 8 cm；坐标轴全框、刻度朝内；图例去底色、去边框；变量符号与单位符合国标。

## 自查清单（改稿时逐条过一遍）

- [ ] 有没有"××不是本文创新点"这类否定式自我降格？
- [ ] 有没有"数据基于××、未重新运行、真实可查"这类自证句？
- [ ] 术语是否用的是领域最通用的形式，且全文一致？
- [ ] 正文是否出现文件名、路径、字节数、哈希值、commit 号？
- [ ] 是否出现"本文基于××撰写""投稿前补充"等写作过程信息？
- [ ] 核心数据表是否在正文，而不是在附录？
- [ ] 有没有口语、借喻、行话或领域撞词？
- [ ] 局限是否集中在讨论部分，而不是散落在正文各处？
- [ ] 是否符合目标期刊对题目、摘要、引言、结论、图表的格式规定？

> **使用提示**：不要只改被点名的那几句。按上面每一类，从头到尾全文排查一遍，把同类问题一并修正。
